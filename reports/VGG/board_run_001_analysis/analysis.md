# VGG16 50 张图片上板结果分析

分析日期：2026-10-22。原始运行目录：`reports/VGG/board_run_001`。本次只读取板测文件，并在独立目录补做 FP32 参照与分析，没有修改原始板测结果、部署代码或 RTL。

## 1. 主要结论

1. 一次下载模型及全部输入、连续执行 50 张图片的流程通过了本次板测。50 张均正常结束，CSR 无错误，末层编号均为 20，周期和输出文件相互吻合。
2. 20,070,400 字节输入的原始载荷、首次 DDR 回读、50 张推理后的末次回读具有相同 SHA256。本次输入库没有被中间特征覆盖。
3. 平均硬件延迟为 7.5924379768 s/张，样本标准差仅 13.5054 μs。整网有效算力为 4.075177 GOPS，相对 28.8 GOPS 理论峰值的效率为 14.1499%。
4. 本次额外使用当前同一 VGG16 checkpoint、相同预处理做了 50 张 FP32 推理，并逐张重算检查输入 BIN。FPGA 与 FP32 的 Top-1 为 50/50 一致，Top-5 类别集合为 50/50 一致。这是两种数值实现的一致性结果，不是带真实标签的分类准确率，也不是整数黄金模型逐位验证。
5. `photo34.jpg` 有一个输出达到 INT16 上限 32767。该类别的 FP32 logit 为 35.67577，超出当前输出格式上限约 31.99902，与输出饱和现象一致；本张 Top-1 没有改变。
6. 文件时间估算显示，权重下载及回读约占本次会话的 73.5%。一次传权重的收益已经得到执行记录支持；硬件计算利用率仍需逐层观测才能解释。

在本次 50 张不同输入的顺序执行中，时延波动很小，未观察到明显的首张额外开销或后段持续变慢。这个结果与固定形状、稠密卷积采用固定计算调度相容，但不能仅靠这些计数断定波动来自 DDR、温度或具体某个模块。

这些时间按硬件周期计算，包括取指、层调度、计算、暂停及板内 DDR 访问。最终 runtime 信息写回阶段不在计数内；JTAG 下载、回读、主机参数更新/软复位等也不在其中。因此 0.131710 FPS 是硬件计时口径下的等效帧率，不是整个调试会话的端到端吞吐量。

此前单图记录 `board_run_002` 为 7591.6292 ms，本次均值高约 0.8088 ms（0.01065%），量级基本一致。两次使用的图片和输入地址不同，不将该差值解释为严格的性能回归或改进。

## 4. 论文四指标的本次结果

计算量按 1 MAC=2 operations，采用当前模型的逻辑通道数和实际输出形状。Conv/FC 操作计入分子，bias、ReLU、池化比较、通道补齐不额外计入；对应耗时保留在整网分母中。

- 卷积：30,693,261,312 operations/图。
- 全连接：247,267,328 operations/图。
- 总计：30,940,528,640 operations/图，即 30.94052864 GOP/图。
- 整网算力：`50 × 每图操作数 / 50张总硬件秒数 / 10^9`，不是逐层算力的算术平均。

| 指标 | 本次结果 | 说明 |
|---|---:|---|
| 计算速度 | 4.075177 GOPS | 以 50 张总操作数除以总时间 |
| 理论峰值 | 28.8 GOPS | 144 DSP × 100 MHz × 2 operations/拍 |
| 吞吐量效率 | 14.1499% | 4.075177 / 28.8 |
| 能源效率 | 暂不能计算 | 尚未找到本工程功耗记录 |
| GOPS/LUT | 0.000121263 | LUT 33606 |
| GOPS/FF | 0.0000983013 | FF 41456 |
| GOPS/BRAM36 | 0.0397578 | BRAM 102.5 个 36 Kb 等效块 |
| GOPS/DSP | 0.0282998 | DSP 144 |

144 DSP 的器件占用率为 65.45%，与算力效率 14.1499% 不是同一概念。现有实现报告同时记录 LUT 63.17%、FF 38.96%、BRAM 73.21%、Slice 90.47%；不能仅凭尚有 DSP 余量就决定扩大 CU。

在理想峰值下，30.940529 GOP 对应约 1.074324 s 的纯乘加时间下界。实际均值约为该下界的 7.07 倍，说明计算资源未持续发挥理想能力；该比值不是可直接实现的加速倍数，也不能把差额全部归因于 DDR。

## 5. FP32 参照与量化观察

参照使用当前 `cnn_scripts/weight/vgg16.pth`，`eval()`、`torch.inference_mode()`、CPU 4 线程，逐张运行同一预处理。50 个待推理张量重新量化后的字节全部与板测输入快照对应片段一致。环境为 PyTorch 2.14.1+cpu、XSDB 2024.2。

Checkpoint SHA256：`397923af8e79cdbb6a7127f12361acd7a2f83e06b05044ddf496e83de57a5bf0`。

| 比较项目 | 结果 |
|---|---:|
| Top-1 一致 | 50/50 |
| Top-5 类别集合一致 | 50/50 |
| Top-5 顺序完全一致 | 49/50 |
| 不同 Top-1 类别数量 | 34 |
| 全部 50000 个反量化 logits 的 MAE | 0.000723165 |
| 全部 logits 的 RMSE | 0.0164645 |
| 最大绝对误差 | 3.676746，photo34.jpg 的上限输出 |
| 排除触及 INT16 端点的 1 个值后的 MAE | 0.000649643 |
| 排除该端点后的最大绝对误差 | 0.00515199 |

唯一的 Top-5 顺序变化是 `photo21.jpg`：FPGA 为 `[371,335,556,743,228]`，FP32 为 `[371,335,743,556,228]`，第三、第四名互换，Top-1 及类别集合没有改变。

`photo34.jpg` 的类别索引 604（标准 ImageNet 类别名 hourglass）在 FPGA 为 32767，输出小数位数为 10，反量化后为 31.9990234；FP32 为 35.6757698。最大误差几乎由这个值主导。该现象与输出饱和一致，应在后续量化检查中保留，但本次没有改变其 Top-1。不能由最终输出未大面积触及端点推断所有中间层都没有饱和。

`photo36.jpg` 和 `photo45.jpg` 的 FPGA Top-1/Top-2 反量化差仅为 0.0107422 和 0.0126953，是后续整数逐位验证值得优先覆盖的样本；本次两张仍与 FP32 Top-1 一致。logit 差值不是经过校准的置信度。

原始板测 `numerical_validation: NOT_PERFORMED` 保持不变。本次新增证据为 FP32 参照一致性，不能据此声明“50 张分类准确率 100%”或“全部整数运算逐位正确”。真实准确率还需要真实标签，整数正确性还需要遵循硬件舍入/饱和/布局合同的整数黄金模型。

## 6. 权重驻留的收益与调试耗时

下表依据原始文件创建/修改时间估算，时区为 Asia/Shanghai。日志没有逐阶段精确定时，文件复制或时间戳变化也会影响估算；这些数值用于解释本次调试耗时构成，不作为硬件性能计数。

| 阶段 | 约耗时 |
|---|---:|
| 整个会话，17:43:02–18:17:26 | 2064.46 s，约 34 分 24 秒 |
| 权重下载及逐块回读校验 | 1517.65 s，约 25 分 18 秒 |
| 合并输入下载及逐块回读校验 | 107.28 s |
| 50 张执行循环，含主机操作和逐图回读 | 383.08 s |
| 输入库末次只读校验 | 49.03 s |

权重阶段约占会话 73.5%，支持此前“权重传输最耗时”的观察。这里包含 PC 经 JTAG 向 DDR 下载及回读校验，不是 PL 推理过程中读取 DDR 的带宽测量。

相对于每张图片都重新下载整个权重包，当前流程避免了 49 次权重上传，少上传 14,055,003,200 字节（约 14.06 GB/13.09 GiB）。也避免了相应的重复权重回读。没有重复运行旧流程，因此不把该字节节省换算为已实测的整体加速倍数。

批量输入和权重驻留主要减少调试传输开销。每次推理仍需由 PL 从 DDR 读取各层权重，因此它们没有直接提高上述 4.075177 GOPS 的核心执行效率。

## 7. 下一步工作优先级

1. 保留本次 50 张作为连续推理回归集，重点包含 photo21、photo34、photo36、photo45。
2. 性能分析优先补 21 层的完成周期快照，按 Conv 块、Pool、FC 分解时间；必要时补计算实际接受拍数、FIFO 暂停及 AXI 握手字节计数。只有这些数据才能判断 14.15% 效率损失主要来自供数、写回、分块还是控制调度。
3. 数值验证补整数黄金输出，区分正常量化差异与 RTL 实现差异；对 photo34 检查末层输出尺度及中间层饱和情况，先量化风险再调整尺度。
4. 补与当前实现和推理窗口匹配的功耗记录，完成 GOPS/W 及 J/图；片上估计和板级实测分别报告。
5. 后续若要精确统计实验总耗时，在下载、回读、推理循环等边界增加显式时间戳；不要用 JTAG 速度推断 DDR 到 PL 的推理供数能力。
